**Last Updated**: 2025-11-18
**Repository**: Personal blog built with Astro

## Overview

This is a personal blog repository built with Astro. The repository uses a dual-branch workflow where the `source` branch contains source code and posts, and the `publish` branch contains the compiled static site.

### Tech Stack

- **Frontend/Build**: Astro (via git submodule `astro-ink`)
- **Content**: Markdown (.md) files (legacy .org files exist but new posts should use .md)
- **Package Manager**: npm (Node.js)
- **Development Environment**: Nix (flake.nix available)

### Legacy Components (No Longer Used)

- **Haskell backend** (Stack, blog.cabal, app/site.hs, MyBlog/ modules) - previously used for Org-mode to Markdown conversion
- **Fomantic UI** - old CSS framework, no longer in use

## Branch Workflow

### Main Branches

- **`source`**: Main development branch (default)
  - Contains source code, posts, and all development files
  - Protected branch - requires PRs for changes
  - Triggers automatic publish workflow on push

- **`publish`**: Deployment branch
  - Contains compiled static site (`_site/` contents)
  - Auto-generated by `make blog-publish`
  - Deployed to GitHub Pages

### Feature Branches

- **`new_post/*`**: Created automatically for new posts from GitHub Issues
- **`claude/claude-md-*`**: AI assistant development branches
  - Must start with `claude/` and end with matching session ID
  - Example: `claude/claude-md-mi34gsby53t2n6r1-01HzRodiptPMBB2XcTMfYvkd`

## Build System

### Makefile Targets

```bash
make blog-build        # Build the blog site
make blog-publish      # Build and publish to publish branch
make test             # Run tests (alias for blog-build)
```

### Build Process (`make blog-build`)

1. Updates git submodules (`git submodule update --init`)
2. Copies posts (`*.md`) to `astro-ink/src/content/blog/`
   - Note: Makefile also copies legacy `*.org` files for backward compatibility
3. Installs npm dependencies in astro-ink
4. Builds Astro site (`npm run build`)
5. Copies output to `_site/` directory

### Publish Process (`make blog-publish`)

1. Runs `make blog-build`
2. Switches to `publish` branch
3. Copies `_site/` contents to root
4. Commits and pushes changes
5. Switches back to previous branch

## Content Management

### Post Formats

- **Markdown** (`.md`): **Current format** - Use this for all new posts
- **Org-mode** (`.org`): **Legacy format** - 129 old posts exist in this format but do not create new .org files

### Blog Metadata System

Posts use YAML frontmatter with the following custom metadata fields:

#### kind (Type of post)
- `Memo`: General notes
- `Diary`: Personal diary entries
- `Knowledge`: Knowledge articles
- `Advertisment`: Promotional content
- `Translation`: Translated articles
- `HowTo`: Tutorial/how-to guides

#### status (Content freshness)
- `Normal`: Standard post
- `Accuracy`: Needs accuracy review
- `Outdated`: Content is outdated
- `Archive`: Archived content

#### progress (Publication state)
- `Empty`: Not started
- `WIP`: Work in progress
- `Published`: Published and complete

#### All Metadata Fields
- `title`: Post title
- `tags`: Space or comma-separated tags (e.g., `github blog` or `tag1, tag2`)
- `author`: Post author (typically "Cj-bc")
- `kind`: Type of post (see values above)
- `status`: Content freshness status
- `progress`: Publication state
- `publishDate`: Publication timestamp (auto-generated in workflows)
- `modDatetime`: Last modification timestamp (auto-updated in workflows)

### Astro Frontmatter Format

Posts in `posts/` directory should follow this frontmatter structure:

```markdown
---
title: Post Title
tags: github blog
author: Cj-bc
kind: Knowledge
status: Normal
progress: WIP
publishDate: 2025-11-17T12:00:00+09:00
modDatetime: 2025-11-17T12:00:00+09:00
---

# Your content starts here

Post content in Markdown format...
```

**Note**: When using the GitHub Issue workflow, `publishDate` and `modDatetime` are automatically generated, so you can omit them from the issue body.

## GitHub Actions Workflows

### Automated Workflows

#### 1. **publish.yaml** - Auto-Publish on Push
- **Trigger**: Push to `source` branch
- **Actions**:
  1. Runs `make blog-publish`
  2. Pushes to `publish` branch
  3. Deploys to GitHub Pages

#### 2. **new-post-from-issues.yaml** - Create Posts from Issues
- **Trigger**: Issue comment creation (owner only)
- **Label Required**: `automation/new-post`
- **Actions**:
  1. Converts issue title to filename (kebab-case)
  2. Creates post file from issue body
  3. Creates PR with branch `new_post/{title}`
  4. Comments progress on issue

**Usage**:
1. Create GitHub Issue with `automation/new-post` label
2. Write post content in issue body with frontmatter
3. Comment on the issue to trigger automation
4. PR will be created automatically

#### 3. **sync-pr-from-issue-update.yaml** - Sync PR When Issue Updates
- **Trigger**: Issue edit (owner only)
- **Label Required**: `automation/new-post`
- **Actions**:
  1. Finds associated PR (via "Closes #N" reference)
  2. Updates post file with new issue content
  3. Commits and pushes to PR branch
  4. Provides detailed status comments

**Features**:
- Skips sync if PR is not open
- Updates `modDatetime` automatically
- Creates detailed progress comments on issue
- Handles workflow failures gracefully

#### 4. **pr-validation.yaml** - Validate PRs
- **Trigger**: PR events or `/test` command in comments
- **Actions**:
  1. Runs `make test`
  2. Comments success/failure status on PR

#### 5. **update-astro-ink-submodule.yaml** - Update Submodule
- **Trigger**: Manual or scheduled
- **Actions**: Updates the astro-ink submodule to latest version

### Testing PRs

Comment `/test` on a PR to trigger validation workflow.

## Development Workflows for AI Assistants

### Creating a New Post

**Option 1: Manual Creation**
1. Create file in `posts/` directory with format: `YYYY-MM-DD-title-in-kebab-case.md`
2. Add proper frontmatter (see Astro Frontmatter Format above)
3. Write content
4. Commit and push to feature branch
5. Create PR to `source` branch

**Option 2: GitHub Issue Workflow**
1. Create GitHub Issue with `automation/new-post` label
2. Include frontmatter and content in issue body
3. Comment on issue to trigger automation
4. PR will be created automatically

### Updating an Existing Post

**If created via GitHub Issue workflow:**
1. Edit the original GitHub Issue
2. Update content in issue body
3. Automation will sync changes to PR

**Manual update:**
1. Edit post file directly in `posts/` directory
2. Update `modDatetime` in frontmatter
3. Commit and push

### Making Code Changes

1. **Always work on feature branch** (never push directly to `source`)
   - For Claude: Use branch format `claude/claude-md-{session-id}`
   - Branch name must start with `claude/` and end with matching session ID

2. **Before making changes:**
   - Update submodules: `git submodule update --init`
   - Install dependencies: `cd astro-ink && npm install`

3. **After making changes:**
   - Test build: `make test` or `make blog-build`
   - Commit with clear messages
   - Push to feature branch: `git push -u origin <branch-name>`
   - Create PR to `source` branch

4. **Commit Message Conventions:**
   - `feat:` - New feature or post
   - `fix:` - Bug fix
   - `chore:` - Maintenance tasks
   - `docs:` - Documentation updates

## Important Notes for AI Assistants

### DO

1. **Always check git submodule status** before building
2. **Run `make test`** before creating PRs
3. **Use proper branch naming** for Claude branches (`claude/claude-md-*`)
4. **Update metadata** when modifying posts (especially `modDatetime`)
5. **Follow frontmatter structure** exactly for new posts
6. **Use GitHub Issue workflow** for creating new posts when appropriate
7. **Check workflow status** after pushing to ensure CI passes
8. **Read existing posts** for style and format reference
9. **Preserve existing metadata fields** when editing posts
10. **Use retry logic** for git operations (up to 4 times with exponential backoff)

### DON'T

1. **Never push directly to `source` or `publish` branches**
2. **Don't modify the astro-ink submodule** without explicit permission
3. **Don't change the build process** without understanding the full workflow
4. **Don't remove metadata fields** from existing posts
5. **Don't create posts without proper frontmatter**
6. **Don't skip `make test`** before creating PRs
7. **Don't use incorrect branch naming** (push will fail with 403)
8. **Don't commit generated files** (_site/, node_modules/, .stack-work/)
9. **Don't break the automation workflows** (they're critical for content management)
10. **Don't modify .github/workflows/** without careful consideration
11. **Don't create new .org files** - use .md format for all new posts
12. **Don't modify legacy Haskell or Fomantic UI code** unless explicitly removing it

## Troubleshooting

### Build Failures

**Submodule not initialized:**
```bash
git submodule update --init
```

**npm dependencies missing:**
```bash
cd astro-ink && npm install
```

**Astro build fails:**
- Check for syntax errors in post frontmatter
- Ensure all .md files have valid YAML frontmatter
- Check `astro-ink` submodule is properly initialized

### Workflow Failures

**PR validation fails:**
- Check `make test` output locally
- Ensure all posts have valid frontmatter
- Verify no broken image links

**Publish workflow fails:**
- Usually due to build errors
- Check submodule status
- Verify npm dependencies

**Issue-to-PR automation fails:**
- Ensure issue has `automation/new-post` label
- Check issue body has valid frontmatter
- Verify commenter is repository owner

### Git Push Failures

**403 Forbidden on push:**
- Check branch naming (must be `claude/claude-md-{session-id}`)
- Verify session ID matches exactly
- Use retry logic with exponential backoff
